> AES-ECB 는 결정적이므로 동일 평문이면 동일 암호문이 나온다. (동시에 ECB 가 운영에서 권장되지 않는 이유이기도 하다.)

| # | 항목 | 확정값 |
|---|---|---|
| B1 | JDBC 스킴 | `jdbc:oracle:thin` — `LIMIT` 없음, `FETCH FIRST` 사용 |
| B2 | 접속정보 필드 | DB `URL`/`ID`/`PASSWORD`/`TABLE`, FTP `URL`/`PORT`/`ID`/`PASSWORD`/`PATH` |
| B3 | 동일 인스턴스 | **예** |
| B4 | FTP / SFTP | 평문 FTP |
| B5 | 업로드 디렉터리 | `Recruit/2026/` |
| B6 | APPLICANT_KEY | 8자 |
| B7 | XML 선언부 | **없음** — 인코딩을 코드가 알고 있어야 함 |
| B8 | 루트 엘리먼트 | **없음** — 파싱 전 `<ROOT>` 래핑 필수 |
| B9 | 샘플 건수 | HEADER 15 / ITEM 70, 최대 1:10 |
| B10 | **대상 환경의 접근 권한** | **append-only · write-only** — DB 는 `SELECT`/`INSERT`/`UPDATE` 만 (`DELETE` 시 `ORA-01031`), FTP 는 `STOR` 만 (`RNFR` 시 `451`, `DELE` 시 `550 Operation not permitted`, **`RETR` 시 `550 Permission denied`**) |

> **B10 이 이 과제의 숨은 제약이다.** 지원자 전원이 같은 테이블과 같은 디렉터리를 공유하므로
> 서로의 제출물을 지우거나 바꾸지 못하게 막아 둔 구성으로 보인다. 두 시스템에 같은 원칙이
> 걸려 있다는 점에서 우연이 아니다.
>
> **FTP 는 `RETR` 까지 막혀 있다** (`550 ... Permission denied` — 2026-07-31 실측).
> 올린 파일을 **되읽어 내용을 확인할 방법이 없다**는 뜻이다. 그래서 업로드 직후의
> **이름·크기 검증(3.7)이 유일한 검증 수단**이 된다 — 받아서 바이트를 대조하는 방법은
> 이 환경에서 애초에 선택지가 아니며, 이는 시연 절차(7.2)도 제약한다.
>
> 이 사실은 보상 트랜잭션 설계(3.9)를 **한 번 뒤집었다**. 되돌리기가 불가능한 환경에서는
> 보상 로직을 정교하게 짜는 것이 아니라 **되돌릴 상태를 만들지 않는 쪽**으로 가야 한다 (D-21).
>
> **`DELE` 금지가 결정적이다.** rename 만 막혔다면 "확정 방법을 바꾸면 된다" 로 끝날 일이지만,
> 삭제까지 막혀 있으므로 초판의 보상 경로(3.9 표 3번 행 — `.tmp` 삭제) 자체가
> **실행 불가능한 코드였다.** 즉 D-21 은 더 나은 선택지가 아니라 **유일한 선택지**다.
>
> **같은 제약이 4.4 에서는 정합성의 근거가 된다.** 아무도 지울 수 없으므로 배치가 읽은 행은
> 사라질 수 없고, 따라서 PK 로 지목한 `UPDATE` 는 반드시 1행에 적용된다.
> 하나의 환경 제약이 한쪽에서는 재설계를 강요하고 다른 쪽에서는 보장으로 쓰인다 —
> 제약을 추측하지 않고 **실측해 문서에 남긴** 값이 여기서 나온다.

## 2. BOOT-000 — 과제 정보 수신

### 2.1 응답 구조 (실측)

```
{
  "APPLICANT_KEY"    : 평문 8자,
  "ORDER_TB_CONN"    : { URL, ID, PASSWORD, TABLE },      // 값마다 개별 AES-128 암호화
  "SHIPMENT_TB_CONN" : { URL, ID, PASSWORD, TABLE },
  "FTP_CONN"         : { URL, PORT, ID, PASSWORD, PATH },
  "SAMPLE_DATA"      : Base64(EUC-KR XML)                 // 암호화 대상 아님
}
```

> **암호화 단위는 블록이 아니라 블록 안의 개별 필드다.** (Base64 24자=16바이트, 64자=48바이트 — 모두 AES 블록 배수)

### 2.2 복호화 규격

```
key    = SHA-1( PHONE_NUMBER.getBytes("UTF-8") )[0..15]
cipher = AES/ECB/PKCS5Padding
plain  = cipher.doFinal( Base64.decode(field) )
```

`SAMPLE_DATA` 는 Base64 디코드 후 **EUC-KR** 로 문자열화한다. UTF-8 로 읽으면 한글이 전부 깨지고 그대로 FTP 영수증까지 전파된다.

### 2.3 파싱 시 주의 (실패 경험 기록)

세 접속정보 블록이 `URL` · `ID` · `PASSWORD` 라는 **동일한 키 이름**을 공유한다.
응답 트리를 전역 평탄화하면 먼저 만난 블록의 값만 남고 나머지는 **조용히 소실**된다.
초판 구현이 이 함정에 빠졌고, 필수 필드 누락으로 즉시 실패(fail-fast)했기에 드러났다.
→ **블록 스코프를 보존하는 명시적 추출**로 교체함 (`ConnBlock`).

### 2.4 보안 취급

복호화 키의 탐색 공간은 국내 휴대폰 번호 약 1억 개다. 암호문을 확보하면 전수 대입이 현실적이므로,
**응답 JSON 은 평문 크리덴셜과 동일 등급**으로 취급한다. `secrets/` 전체가 `.gitignore` 대상.

## 3. IF-ORD-001 — 주문 생성 연계 (Real-time / SYNC)

### 3.1 개요

| 항목 | 내용 |
|---|---|
| 트리거 | 주문자의 주문 생성 API 호출 |
| 입력 | XML (EUC-KR, 선언부·루트 없음) |
| 출력 | Oracle INSERT + 구분자 텍스트 파일 FTP 전송 |
| 응답 | JSON |
| 성격 | 동기. **JDBC · FTP 양쪽 모두 성공해야 성공 응답** |

### 3.2 소스 구조

`HEADER : ITEM = 1 : N`, 조인 키 `USER_ID`.

**샘플 데이터 실측**

```
HEADER 15건 / ITEM 70건
  ├─ 정상 매칭 : USER01~USER11 (11건) → ITEM 63건  (최대 USER09 = 10건)
  ├─ 고아 ITEM : USER16~USER22 (7건) — 대응 HEADER 없음
  └─ 빈 HEADER : USER12~USER15 (4건) — 대응 ITEM 없음
```

- HEADER `USER_ID` 중복 0건 → 조인 모호성 없음
- **ITEM 이 HEADER 순서대로 정렬돼 있지 않다.** 문서 순서 의존 파싱은 즉시 깨진다 — 반드시 `USER_ID` 로 조인
- 전 필드 공백/개행 없음(`TrimDiff=0`), 빈 값 없음. `STATUS` 는 15건 모두 `N`
- 그럼에도 `trim` 은 방어적으로 유지한다 (PDF 예시에는 개행이 포함돼 있었다)

### 3.3 유효성 검증 — 두 범주로 분리

| 범주 | 규칙 | 성격 | 처리 |
|---|---|---|---|
| **구조 오류** | V-01 HEADER 필수 필드<br>V-02 ITEM 필수 필드<br>V-05 PRICE 숫자 형식<br>V-06 길이 초과 | 메시지 자체가 깨짐 | **요청 전체 거부**. Receiver 호출 전 차단 |
| **정합성 불일치** | V-03 고아 ITEM<br>V-04 ITEM 없는 HEADER | 메시지는 정상, 대응 대상 없음 | **건 단위 스킵 + 경고 로그**, `RESULT=PARTIAL` |

> **왜 부분 처리인가 (D-02).** 과제가 제공한 샘플에 이상 데이터 11건이 의도적으로 심어져 있다.
> 전체 거부를 택하면 샘플로는 **단 한 건도 적재할 수 없다.** 송신 시스템의 데이터 불완전성 때문에
> 정상 63건까지 멈추는 것은 EAI 의 태도가 아니다.
> 단, **버린 건수를 반드시 드러낸다.** 조용히 63건만 넣고 성공이라 답하는 것이 진짜 사고다.

**V-06 길이 기준** — 대상 컬럼이 전부 `VARCHAR2(100 BYTE)` 이므로 **UTF-8 바이트 길이 100** 이 상한이다.

| 필드 | 샘플 최대 Char | 샘플 최대 **Byte** | 상한 |
|---|---|---|---|
| USER_ID / ITEM_ID / PRICE | 6 | 6 | 100 |
| NAME | 3 | 9 | 100 |
| ADDRESS | 10 | 28 | 100 |
| ITEM_NAME | 7 | 21 | 100 |

### 3.4 카디널리티

```
HEADER 1건 × 해당 USER_ID 의 ITEM n건  →  ORDER_TB n행  =  영수증 파일 n라인
샘플 기준: 63행 / 63라인 (70건 중 7건 스킵)
```

조인 후 평탄화(flatten)가 Mapper 의 핵심 로직이다.

### 3.5 Target A — ORDER_TB (JDBC Receiver)

| # | 컬럼 | 타입 | Source | 규칙 |
|---|---|---|---|---|
| 1 | `ORDER_ID` | VARCHAR2(100) **PK** | — | 자체 채번 `[A-Z][0-9]{3}` |
| 2 | `APPLICANT_KEY` | VARCHAR2(100) **PK** | BOOT-000 | 전 행 고정값 |
| 3 | `USER_ID` | VARCHAR2(100) | HEADER | 원본 유지 |
| 4 | `ITEM_ID` | VARCHAR2(100) | ITEM | 원본 유지 |
| 5 | `NAME` | VARCHAR2(100) | HEADER | 원본 유지 |
| 6 | `ADDRESS` | VARCHAR2(100) | HEADER | 원본 유지 (내부 공백 보존) |
| 7 | `ITEM_NAME` | VARCHAR2(100) | ITEM | 원본 유지 |
| 8 | `PRICE` | VARCHAR2(100) | ITEM | **문자열 그대로.** 숫자 검증만, 포맷 변경·콤마 삽입 금지 |
| 9 | `STATUS` | VARCHAR2(100) | HEADER | trim 후 `N` |
| 10 | `CREATE_TIME` | TIMESTAMP(6) | — | **DEFAULT `SYSDATE`. INSERT 목록에서 제외한다** |

- PK: `(ORDER_ID, APPLICANT_KEY)` 복합
- Batch INSERT, 파라미터 바인딩 필수(문자열 결합 SQL 금지). 실패 시 전체 롤백
- 배치 결과 검증은 **합산이 아니라 개수**로 한다. JDBC 는 성공을 `SUCCESS_NO_INFO`(`-2`) 로 돌려줄 수 있어, 합산하면 멀쩡한 적재가 실패로 뒤집힌다. 이 판정은 두 인터페이스가 `JdbcBatches` 로 공유한다
- 테이블명은 바인딩할 수 없어 유일하게 문자열로 조립되는 값이다. 출처가 BOOT-000 산출물이라도 식별자 규격 검증을 거친다 (`SqlIdentifiers`)
- `STATUS` 값 어휘는 `OrderStatus` 열거형 한 곳에 있다. IF-SHP-001 이 조회 조건과 갱신 값으로 같은 값을 쓰므로, 리터럴을 각자 들면 한쪽만 바뀌었을 때 **배치가 조용히 0건을 처리한다**

### 3.6 Target B — 영수증 파일 (FTP Receiver)

**파일명**

```
INSPIEN_{참여자명}_yyyyMMddHHmmss.txt
```

- 참여자명 **한글**, 타임스탬프는 인터페이스 실행 시작 시각(전 라인 동일)
- **파일명 인코딩: UTF-8** (근거는 3.7)

**라인 포맷** — 8필드, 구분자 `^`, 종결 `\n`

```
ORDER_ID ^ USER_ID ^ ITEM_ID ^ APPLICANT_KEY ^ NAME ^ ADDRESS ^ ITEM_NAME ^ PRICE \n
```

**확정 사항 (위반 시 감점)**

- `STATUS` 는 파일에 **포함되지 않는다** (DB 9필드 / 파일 8필드)
- **필드 순서가 DB 컬럼 순서와 다르다.** DB 3·4번은 `USER_ID`·`ITEM_ID` 이나 파일은 2·3·4번이 `USER_ID`·`ITEM_ID`·`APPLICANT_KEY` 다. DB 컬럼 순서를 그대로 join 하면 오답
- 구분자 `^`, 종결자 `\n` 고정. 마지막 라인에도 `\n` 부여
- 값에 구분자·개행이 섞이면 **실패시킨다**. 이 포맷에는 이스케이프 규칙이 없어, 그대로 내보내면 수신 측이 **정상 파일로 파싱해** 엉뚱한 값을 배송 정보로 쓴다
- 대상 인코딩으로 표현할 수 없는 문자도 **사전 차단**한다. `String.getBytes()` 는 그런 문자를 예외 없이 `?` 로 바꾸며, 이는 파일명이 `?` 로 깨진 것과 **정확히 같은 종류의 사고**다
- 전송 모드 **binary** (ASCII 모드는 개행 변조 위험)
- **파일 내용 인코딩: EUC-KR** (D-07)

### 3.7 인코딩 결정 — 파일명과 내용은 별개다

| 대상 | 결정 | 근거 |
|---|---|---|
| 파일 **이름** | **UTF-8** | 서버가 `FEAT` 에서 UTF8 지원을 선언한다. **실측으로 보존 확인됨** |
| 파일 **내용** | **EUC-KR** (설정 외부화) | 원본 XML 인코딩 계승 |

> **기존 파일 실측.** 업로드 디렉터리의 53개 파일 중 한글 이름은 전부 `INSPIEN_???_...` 형태다.
> UTF-8 · EUC-KR 양쪽으로 리스팅했을 때 **비ASCII 문자가 0자**로 나왔다 —
> 즉 서버에 저장된 바이트 자체가 리터럴 물음표(`0x3F`)다. 우리가 잘못 읽은 것이 아니라,
> **다른 지원자의 클라이언트가 인코딩 불가 문자를 `?` 로 치환한 채 업로드한 것**이다.
> (`INSPIEN_KDH00020_...` 처럼 한글을 아예 포기한 파일도 섞여 있다.)

**구현 요건 (원인 규명).** 다른 지원자의 파일이 `?` 가 된 원인은 서버가 아니라 클라이언트다.
`commons-net` 의 제어 채널 인코딩 기본값은 `ISO-8859-1` 이라, 여기에 한글 파일명을 실으면
인코딩 불가 문자가 `0x3F`(`?`)로 치환된 채 전송된다. **예외도 나지 않고 조용히 깨진다.**
따라서 FTP Receiver 는 다음을 **로그인 전**에 수행한다.

| 순서 | 조치 |
|---|---|
| 1 | `ftp.setControlEncoding("UTF-8")` — 기본값 `ISO-8859-1` 을 반드시 덮어쓴다 |
| 2 | `FEAT` 응답에 `UTF8` 이 있으면 `OPTS UTF8 ON` 전송 |
| 3 | 로그인 → `setFileType(BINARY_FILE_TYPE)` → `enterLocalPassiveMode()` |
| 4 | 업로드 후 리스팅해 **보낸 이름과 완전히 같은 이름 + 같은 크기**가 있는지 검증 |

> 4번을 넣는 이유: 인코딩 사고는 **예외 없이 성공으로 보고된다.**
> 스스로 확인하지 않으면 면접 시연 자리에서 처음 알게 된다.
>
> "비ASCII > 0" 대신 **완전 일치**를 보는 이유는 치환·절단·정규화 중 무엇이 일어나도 걸리고,
> 참여자명이 영문인 경우에도 오판이 나지 않기 때문이다. 크기까지 보는 이유는 3.9 참조.

### 3.8 ORDER_ID 채번

**과제가 지시한 것과 우리가 정한 것을 구분한다.**

| 항목 | 결정 | 출처 |
|---|---|---|
| 형식 `[A-Z][0-9]{3}` | 대문자 1 + 숫자 3 (`A113`) | **과제 PDF p.5 명시** (`SHIPMENT_ID` 는 p.6, "자동 채번이 아니므로 지원자가 삽입") |
| 공간 26 × 1,000 = **26,000개** | 유한함을 인지하고 소진을 설계에 포함 | 형식에서 유도. PDF 는 공간 크기·소진 처리를 언급하지 않음 |
| 부여 단위 = **주문 라인(행)** | 헤더 단위 아님 | **우리 결정 (D-03).** PK 가 `(ORDER_ID, APPLICANT_KEY)` 이고 `APPLICANT_KEY` 는 전 행 고정값이므로, 한 HEADER 에 ITEM 이 2건이면 행 단위 외의 선택지가 PK 위반이다 |
| 진행 방식 = **순차 증가** | 무작위 아님 | 우리 결정. 재현성·추적성 우위 |
| 구현 = Redis `INCRBY` | 배치 단위 선점 | 우리 결정 (D-09) |

> **근거 정정.** 이전 판은 "샘플의 `A113`/`B114` 가 행 단위를 지시한다" 고 적었으나 이는 근거로 쓸 수 없다.
> PDF 예시는 USER1 · USER2 가 각각 ITEM 1건씩인 **1:1 케이스뿐**이라 행 단위와 헤더 단위를 구분해 주지 못한다.
> 논리적으로 닫힌 근거는 위 표의 **PK 제약**이며, 샘플은 그것과 모순되지 않는다는 방증에 그친다.

**채번 순서 (Redis `INCRBY`)**

```
end   = INCRBY eai:seq:order <행 수>      // 63행이면 왕복 1회로 63개 선점
start = end - 행 수 + 1
index = start-1 … end-1                   // 0-based
ORDER_ID = ('A' + index/1000) + %03d(index%1000)
```

- 행마다 `INCR` 을 부르지 않는다. 63왕복이 1왕복이 되는 것보다, **전량 선점에 실패하면 한 건도 만들지 않는다**는 성질이 중요하다
- 사전식 정렬 순서 = 채번 순서 (`A000` < `A999` < `B000` < `Z999`). 앞자리 문자 + 고정 3자리 제로패딩이므로 성립하며, 이 성질 덕에 `MAX(ORDER_ID)` 를 카운터 복원 기준으로, 그리고 **`ORDER_ID` 를 배치의 폴링 커서로** 쓸 수 있다 (4.6)
- `SHIPMENT_ID` 는 **별개 카운터**(`eai:seq:shipment`)다. 공유하면 26,000 공간을 둘이 나눠 쓰고, 주문 채번의 소진이 배송 채번을 함께 끌어내린다

**공간 소진 (26,000 도달)**

| 대상 | 처리 |
|---|---|
| 운영 | `EAI-4003 ID_SPACE_EXHAUSTED` 로 **실패**. 재시도 불가로 분류하고 되감기(`DECRBY`)하지 않는다 |
| 개발 | 코드가 아니라 **별도 도구**로 리셋 — `tools/reset-sequence.ps1` |

> 되감지 않는 이유: 실패한 요청이 번호를 태우는 손해보다, 되감기와 다른 요청의 선점이 경합해
> **같은 번호가 두 번 발급되는 사고**가 비교할 수 없이 크다. 이미 소진된 시점이라 태울 번호도 남아 있지 않다.
>
> 리셋을 코드에 두지 않는 이유: 카운터를 되돌리는 경로가 애플리케이션 안에 있으면
> 언젠가 설정 실수로 운영에서 실행된다. 개발 편의는 운영 경로 밖에 둔다.

**Redis 데이터 유실 대비 (폴백 재설계)**

초판은 "Redis 미가용 시 DB 시퀀스 테이블" 을 폴백으로 적었으나 **철회한다.**
시퀀스 테이블을 만드는 것은 대상 스키마에 손을 대는 일이고, 이는 이 과제의 전제인
**"기존 시스템의 스펙은 불변 조건"** 과 정면으로 충돌한다.

| 상황 | 처리 |
|---|---|
| Redis 일시 단절 | `EAI-4002 ID_ISSUE_FAILED` (**재시도 가능**). 대체 채번기로 몰래 넘어가지 않는다 — 두 채번기가 동시에 살아 있으면 중복이 난다 |
| Redis 데이터 유실 (컨테이너 초기화 등) | 기동 시 `SELECT MAX(<ID컬럼>) FROM <테이블> WHERE APPLICANT_KEY = ?` 로 카운터를 **시딩**. 읽기 전용이라 스키마를 건드리지 않는다. **두 카운터 각각 수행한다** |

> 시딩이 있으면 Redis 는 "진실의 원천" 이 아니라 **동시성 조정 계층**이 된다.
> 진실은 이미 적재된 데이터에 있고, Redis 는 그 다음 번호를 빠르고 원자적으로 나눠 줄 뿐이다.
> 이 구도라야 `docker compose down -v` 한 번에 정합성이 깨지지 않는다.

> **정합성 요건.** 파일 라인과 DB 행은 동일한 `ORDER_ID` 를 공유해야 한다.
> Mapper 가 표준 레코드 리스트를 **한 번** 생성하고, 두 Receiver 가 그 **동일 리스트**를 각자 소비한다.
> 두 Receiver 가 각자 채번하면 정합성이 즉시 깨진다.

### 3.9 JDBC ↔ FTP 동기화 (보상 트랜잭션)

FTP 는 DB 트랜잭션에 참여할 수 없어 2PC 를 쓸 수 없다. 보상 방식으로 처리하되,
**준비 단계에서 원격에 쓰기를 하지 않는다** (B10 · D-21).

| 순서 | 동작 | 서버 상태 | 실패 시 |
|---|---|---|---|
| 1 | DB 트랜잭션 시작 → ORDER_TB INSERT (**commit 보류**) | DB에 미확정 행 | 즉시 롤백, 실패 응답 |
| 2 | FTP 접속 + 영수증 내용 생성 (**업로드 안 함**) | **없음** | DB 롤백, 실패 응답 |
| 3 | DB commit | **없음** | 보상할 것이 없다 → 온전한 실패, 재시도 안전 |
| 4 | **최종 파일명으로 STOR** + 이름·크기 검증 | 영수증 존재 | **수동 조치 대상 기록** (`EAI-3005`). DB 는 롤백하지 않음 |
| 5 | 성공 응답 반환 | — | — |

**3번 행이 이 설계의 이유다.** 초판은 이 자리에서 업로드된 `.tmp` 를 삭제해야 했고,
**그 삭제가 이 서버에서는 불가능했다.** 지금은 지울 것이 애초에 없다.

**잃은 것도 적는다.** 최종 파일명으로 바로 올리므로, 전송이 중간에 끊기면
**잘린 파일이 최종 이름을 달고 남고 삭제 권한이 없어 회수할 수 없다.** `.tmp` 였다면
수집 대상 패턴에라도 안 걸렸을 것이다. 없앨 수 없으므로 **반드시 검출한다** —
업로드 직후 리스팅으로 이름뿐 아니라 **크기까지** 대조하고, 어긋나면 `EAI-3005` 로 넘긴다.

- 대안(트랜잭셔널 아웃박스, 최종적 일관성) 비교는 발표 자료에 포함

### 3.10 응답 포맷 (JSON)

| 필드 | 설명 |
|---|---|
| `result` | `SUCCESS` / `PARTIAL` / `FAIL` |
| `ifId` | `IF-ORD-001` |
| `txId` | 추적용 트랜잭션 ID (UUID) |

> 샘플 기준 기대 응답: `processedCount=63`, `skippedCount=11`, `result=PARTIAL` — **실측 일치 확인됨**

**엔드포인트**

```
POST /api/v1/orders
Content-Type: 제한하지 않음 (본문 바이트만 사용)
```

**HTTP 상태 코드 매핑 (D-19)** — 두 인터페이스가 `InterfaceHttpStatus` 로 공유한다.

| 결과 | 상태 | 의미 |
|---|---|---|
| `SUCCESS` / `PARTIAL` | **200** | 요청 처리는 정상 종료. 결과는 본문의 `result` 로 판단한다 |
| `FAIL` + `EAI-1xxx` | **400** | 메시지 자체의 문제 — **송신 측이 고쳐야 한다** |
| `FAIL` + 2xxx/3xxx/4002/4006 재시도 가능 | **503** | 대상 시스템·인프라 일시 장애 — 잠시 후 동일 요청 재전송 |
| `FAIL` + 2xxx/3xxx 재시도 불가 | **502** | 대상 시스템에서 확정 실패 |
| `FAIL` + `EAI-4001` | **409** | 배치 겹침 방지 — 서버 결함이 아니라 상태 충돌 |
| `FAIL` + 나머지 `EAI-4xxx` | **500** | 우리 쪽 문제 — 송신 측이 할 수 있는 일이 없다 |

> **`PARTIAL` 에 `errorCode` 가 실릴 수 있다.** 보상 트랜잭션이 되돌릴 수 없는 자리에서
> 실패한 경우(3.9 표 4번, D-14)이며, 이때도 상태는 **200** 이다.
> 5xx 를 주면 호출자의 재시도가 돌고 **이미 적재된 63행이 한 번 더 들어간다.**
>
> 구현은 `default` 없는 exhaustive switch 다. 에러 코드를 추가하면 **매핑을 정하기 전까지
> 컴파일이 깨진다** — 실제로 `EAI-4006` 을 추가할 때 이 스위치가 먼저 깨졌고,
> 그래서 503 으로 분류하는 판단을 빠뜨릴 수 없었다.

## 4. IF-SHP-001 — 운송사 전송 배치 (Batch / ASYNC)

### 4.1 개요

| 항목 | 내용 |
|---|---|
| 트리거 | 스케줄러 5분 주기 (`fixedDelay`, 값 외부화) **+ 수동 API** (운영·시연용) |
| Source | ORDER_TB (JDBC Polling, 커서 페이징) |
| Target | SHIPMENT_TB + ORDER_TB 상태 갱신 (**동일 트랜잭션**) |
| 성격 | 비동기. 부분 실패 허용, 미처리 건 자연 재처리 |
| 동시 실행 | Redis 분산 락으로 1개 |

시나리오 1 과 **동일한 Sender/Mapper/Receiver 파이프라인을 재사용**한다.
`OrderRestSender` → `JdbcPollingSender` 로 바뀌는 것이 본질적인 차이이며,
Validator · Mapper · Receiver 의 **계약**, 전달 조율자, 실행 이력 로거는 그대로다.

**실시간과 배치의 차이가 구조에 드러나는 지점 (과제 요구 3번째 기준)**

| | IF-ORD-001 (SYNC) | IF-SHP-001 (ASYNC) |
|---|---|---|
| 무엇을 처리할지 정하는 주체 | 송신 측 (보내온 것) | **우리** (조회 조건) |
| 파이프라인 실행 횟수 | 요청당 1회 | **청크마다 반복** |
| 동시 실행 | 제한 없음 (요청마다 독립) | **분산 락으로 1개** |
| 실패의 의미 | 호출자가 고쳐 다시 보낸다 | 호출자가 없다 → **다음 주기가 자연 재처리** |
| 이상 데이터 | 구조 오류는 **전체 거부** | **전부 건 단위 스킵** (D-23) |

### 4.2 Source — 조회 (Oracle 문법 · 커서 페이징)

**첫 청크**

```sql
SELECT ORDER_ID, ITEM_ID, ADDRESS
  FROM ORDER_TB
 WHERE APPLICANT_KEY = ?
   AND STATUS = ?              -- 'N' (OrderStatus.UNSENT)
 ORDER BY ORDER_ID
 FETCH FIRST ? ROWS ONLY
```

**두 번째 청크부터** — 이미 읽은 구간을 지나친다 (근거는 4.6)

```sql
SELECT ORDER_ID, ITEM_ID, ADDRESS
  FROM ORDER_TB
 WHERE APPLICANT_KEY = ?
   AND STATUS = ?
   AND ORDER_ID > ?            -- 직전 청크에서 '읽은' 마지막 ORDER_ID
 ORDER BY ORDER_ID
 FETCH FIRST ? ROWS ONLY
```

- `APPLICANT_KEY` 조건 **필수**. 누락 시 타 지원자 데이터를 읽어 우리 SHIPMENT_TB 에 적재하고 **그쪽 STATUS 를 'Y' 로 바꾼다.** append-only 환경이라 되돌릴 수 없으므로, 이 값은 `String` 이 아니라 `ApplicantKey` 전용 타입으로 전달한다
- `LIMIT` 은 Oracle 에 없다. `FETCH FIRST … ROWS ONLY` (12c+), 바인드 변수 허용
- **조회 컬럼은 3개뿐이다.** `SELECT *` 를 쓰지 않는 이유는 성능이 아니라 개인정보다 — 운송사에 넘기지 않기로 한 `NAME` 이 애플리케이션 메모리·스택트레이스를 통과하게 된다. **필드 축소는 Mapper 가 아니라 Sender 에서 시작한다**
- `ORDER BY ORDER_ID` **필수**. 정렬 없는 `FETCH FIRST` 는 "아무 100건" 이므로 커서 전진의 근거가 사라진다. 채번 형식 덕에 이 정렬은 곧 **발생 순서**이기도 하다 (3.8)
- 청크 크기 기본 **100**, 설정 외부화

**커서용 SQL 을 둘로 나눈 이유.** 첫 청크에 "모든 값보다 작은 초기 커서" 를 넘겨 문장을 하나로
합칠 수도 있으나 하지 않았다. Oracle 에서 **빈 문자열은 `NULL`** 이므로 `ORDER_ID > ''` 는
참이 되지 않고 **예외 없이 0건**을 돌려준다 — "미전송 주문이 없다" 로 보인다.
`'0'` 같은 리터럴 센티널은 `NLS_SORT` 설정에 따라 순서가 달라질 수 있다.
문장을 둘로 두는 쪽이 **가정을 하나도 하지 않는** 길이다.

**`SELECT … FOR UPDATE` 미채택 (D-05).** 조회와 갱신 사이에 끼어들 주체가 없다 —
`STATUS` 를 바꾸는 것은 이 배치뿐이고, 배치는 분산 락으로 하나만 돈다.
IF-ORD-001 은 새 행을 INSERT 할 뿐 기존 행의 상태를 건드리지 않는다.
행 잠금을 걸면 얻는 것 없이 커밋까지 잠금을 붙잡는다. 다중 인스턴스로 확장한다면
상태 선점(`N`→`P`)이 `FOR UPDATE` 보다 낫다 — 잠금은 커넥션이 끊기면 풀리지만 상태는 남는다.

### 4.3 Target — SHIPMENT_TB

| # | 컬럼 | Source | 규칙 |
|---|---|---|---|
| 1 | `SHIPMENT_ID` | — | 자체 채번 `[A-Z][0-9]{3}`. **`ORDER_ID` 와 별개 카운터** |
| 2 | `APPLICANT_KEY` | BOOT-000 | 고정값 |
| 3 | `ORDER_ID` | ORDER_TB | 원본 유지 (원본 참조) |
| 4 | `ITEM_ID` | ORDER_TB | 원본 유지 |
| 5 | `ADDRESS` | ORDER_TB | 원본 유지 |
| 6 | `CREATE_DATE` | — | **DEFAULT `SYSDATE`. INSERT 목록에서 제외** |

**행 대응**: ORDER_TB 1행 → SHIPMENT_TB 1행 (1:1)

> **의도적 필드 축소.** `NAME` · `ITEM_NAME` · `PRICE` · `STATUS` 는 전달하지 않는다.
> 운송사는 배송에 필요한 정보만 받으면 된다 — "수신 시스템이 필요로 하는 것만 변환해 전달"이라는
> EAI 기본 태도의 직접적 구현이다.
>
> `PRICE` 가 특히 그렇다. 넘기면 운송사 시스템이 그 값에 의존하기 시작하고(예: 보험 산정),
> 그 순간 쇼핑몰의 가격 정책 변경이 **운송사 시스템을 깨뜨리는** 관계가 만들어진다.
> 시스템 사이의 결합은 이렇게 "일단 다 보내 두자" 에서 생긴다.

> **`SHIPMENT_ID` 를 `ORDER_ID` 로 재사용하지 않는 이유.** 두 테이블은 서로 다른 시스템의 것이고
> 식별자 체계도 각자의 것이다. 재사용하면 **운송사 PK 가 쇼핑몰 채번에 종속**되어,
> 한 주문이 여러 배송으로 나뉘는 변경이 오는 순간 구조가 무너진다.
> 원본과의 연결은 `ORDER_ID` 컬럼이 담당한다 — 그것이 참조가 하는 일이다.

> **주의**: 등록일시 컬럼명이 두 테이블에서 다르다. ORDER_TB 는 `CREATE_TIME`, SHIPMENT_TB 는 `CREATE_DATE`.
> 공통 매퍼로 뭉뚱그리면 틀린다. 양쪽 모두 이 컬럼을 **아예 다루지 않으므로** 실수가 발생할 자리가 없다.

### 4.4 후행 처리 — 상태 갱신

```sql
UPDATE ORDER_TB
   SET STATUS = ?              -- 'Y' (OrderStatus.SENT)
 WHERE ORDER_ID = ?
   AND APPLICANT_KEY = ?
```

- **적재 성공 건에 대해서만** 수행
- SHIPMENT INSERT 와 **동일 트랜잭션**. 두 테이블이 동일 인스턴스·동일 계정이므로 단일 `DataSource` 로 가능 (B3 / D-04)

**분리하면 반드시 사고가 난다.**

| 순서 | 중간에 실패하면 | 결과 |
|---|---|---|
| INSERT 커밋 → UPDATE 실패 | 적재됐는데 `STATUS='N'` | **다음 주기가 같은 주문을 또 보낸다** (이중 배송) |
| UPDATE 커밋 → INSERT 실패 | `STATUS='Y'` 인데 배송 지시 없음 | **주문이 영구 유실된다** (조회 조건에 다시 안 걸림) |

둘 중 어느 쪽도 예외로 드러나지 않는다. 전자는 물건이 두 번 가고, 후자는 고객이 못 받는다.
그리고 이 환경은 append-only 여서 **되돌릴 수 없다.**

**`AND STATUS = 'N'` 을 붙이지 않는다.** 보호가 생기는 것처럼 보이지만 실제로는
**0행 갱신이 정상인지 이상인지 구분할 수 없게** 만든다. PK 로 지목한 행은
방금 `STATUS='N'` 으로 조회된 행이고 아무도 지울 수 없으므로, 조건을 더 붙여 얻을 것이 없다.

**"정확히 1행 갱신"을 검증하지 않는 이유.** Oracle 드라이버는 배치 원소로
`SUCCESS_NO_INFO`(`-2`)를 흔히 돌려준다 — **영향 행 수를 알려 주지 않는다는 뜻**이다.
문장마다 `executeUpdate()` 로 바꾸면 셀 수 있지만 왕복이 청크 크기만큼 늘어난다.
그 대가를 치르지 않는 근거는 셋이다.

1. `STATUS` 를 바꾸는 주체가 **이 배치뿐**이고, 배치는 분산 락으로 하나만 돈다
2. IF-ORD-001 은 새 행을 INSERT 할 뿐 기존 행의 상태를 건드리지 않는다
3. 대상 환경에 `DELETE` 권한이 없으므로 **조회한 행이 사라질 수 없다** (B10)

즉 PK 로 지목한 행은 반드시 존재하고 반드시 `'N'` 이다. 대신 **문장 개수**는 검증한다
(`JdbcBatches` — 응답 개수 불일치 또는 `EXECUTE_FAILED` 는 실패). 이 전제 중 하나라도
깨지면(다중 인스턴스 운영 등) 여기를 다시 설계해야 하며, 그때는 상태 선점 패턴이 답이다.

### 4.5 유효성 검증 — 전부 건 단위 스킵 (D-23)

| ID | 규칙 | 사유 코드 | 처리 |
|---|---|---|---|
| V-07 | `ORDER_ID` 또는 `ITEM_ID` 가 비어 있음 | `MISSING_ORDER_KEY` | 건 단위 스킵 |
| V-08 | `ADDRESS` 가 비어 있음 | `MISSING_SHIPPING_ADDRESS` | 건 단위 스킵 |

**"우리가 넣은 데이터인데 왜 또 검증하는가."** 정당한 물음이고, 답은 `ORDER_TB` 의 컬럼이
**NULL 을 허용한다**는 것이다 (1.1 실측 — `ORDER_ID`·`APPLICANT_KEY` 만 `NOT NULL`).
우리 Validator 를 거치지 않은 행이 섞일 경로가 실제로 있다 — 검증이 없던 이전 버전이 적재한 행,
사람이 SQL 로 직접 넣은 행(시연 준비 중 흔히 한다).

> 이것이 EAI 의 기본 태도이기도 하다 — **송신 시스템이 온전할 것이라고 전제하지 않는다.**
> 여기서 `ORDER_TB` 는 우리 것이 아니라 **송신 시스템**이다. 우리가 방금 그 시스템에 데이터를
> 넣었다는 사실은 우연이고, 인터페이스의 계약은 그 우연에 기대지 않는다.

**치명적 위반(전체 거부)을 두지 않는 이유.** IF-ORD-001 은 호출자가 기다리고 있어 고쳐
다시 보낼 수 있다. 배치에는 그 호출자가 없다. 전체 거부는 이번 주기에 아무것도 처리하지
않는다는 뜻이고, 다음 주기도 같은 행을 만나 같은 판단을 한다 —
**잘못된 1건 때문에 정상 99건이 영구히 배송되지 않는다.**

**길이 검증(V-06)을 하지 않는다.** `ORDER_TB` 와 `SHIPMENT_TB` 의 대응 컬럼이 모두
`VARCHAR2(100 BYTE)` 로 같다(4.3 실측). 원본에 들어갈 수 있었던 값은 대상에도 반드시 들어가므로
초과가 **구조적으로 불가능**하다. **검증은 방어가 아니라 판단이다** — 일어날 수 없는 일을
검사하는 코드는 읽는 사람에게 "이 경우가 일어날 수 있다" 는 잘못된 정보를 주고,
정작 일어나는 일(빈 배송지)에 대한 주의를 흐린다.

**스킵된 행의 운명 — 한계를 적는다.** 스킵하면 `STATUS='N'` 으로 남고 다음 주기가 다시 읽는다.
5분마다 같은 경고가 반복된다는 뜻이다. 선택지를 모두 검토했다.

| 대안 | 왜 안 되는가 |
|---|---|
| `STATUS='E'` 로 밀어낸다 | 대상 시스템의 **어휘를 우리가 늘리는 일**. "기존 스키마는 불변 조건" 과 충돌하고, 그 값을 해석할 수 있는 시스템은 우리뿐이 된다 |
| 빈 배송지째 적재하고 `'Y'` 로 닫는다 | **다시 다룰 기회가 사라진다.** append-only 라 되돌릴 수 없다 |
| 별도 오류 테이블에 격리한다 | DDL 권한이 없다 |

따라서 **반복을 감수하고 매번 기록한다.** 반복되는 경고는 잡음이 아니라
"원본 데이터를 고쳐야 한다" 는 지속적 신호이며, 조치 주체는 `ORDER_TB` 의 소유자다.

### 4.6 청크 반복과 종료 조건 (D-26)

전체를 메모리에 올리지 않기 위해 청크로 자른다. 그런데 **스킵과 폴링이 만나면 함정이 생긴다.**

조회 조건이 `STATUS='N'` 이고 스킵된 행은 상태가 바뀌지 않으므로, 같은 조건으로 다시 조회하면
그 행이 또 나온다. 순진하게 "0건 나올 때까지" 반복하면 세 가지가 동시에 망가진다.

1. **무한 루프** — 스킵된 행이 청크를 채우면 매번 같은 결과가 돌아온다
2. **집계 부풀림** — 같은 행이 청크마다 스킵으로 다시 집계되어, 스킵 11건이 응답에는 40건으로 나간다
3. **로그 폭증** — 같은 `ORDER_ID` 경고가 한 실행 안에서 반복된다

`OFFSET` 도 답이 아니다. 처리한 행은 `'Y'` 로 바뀌어 조회 대상에서 빠지므로 결과 집합 자체가
줄어들고, 고정 `OFFSET` 을 더하면 **아직 처리하지 않은 행을 건너뛴다.**

**해법 — keyset 페이징.** 읽은 마지막 `ORDER_ID` 를 기억해 그 뒤부터 읽는다 (4.2).

| 항목 | 규격 |
|---|---|
| 커서 전진 기준 | **조회된 마지막 행** (처리 성공한 마지막 행이 아니다). 스킵된 꼬리를 지나쳐야 다시 읽지 않는다 |
| 성립 근거 | `[A-Z][0-9]{3}` + 고정 제로패딩 → 사전식 정렬 = 채번 순서, 전 문자 ASCII (3.8) |
| 커서 영속화 | **하지 않는다.** 실행 안에서만 유효 |
| 종료 조건 | ① 0건 조회 ② 청크가 덜 찼다 ③ 청크 상한 도달 |

> **커서를 저장하지 않는 이유.** 저장하면 "커서보다 작은 미처리 행" 이 영구 유실된다.
> 실행마다 처음부터 다시 읽으므로, 어떤 이유로 이번에 빠진 행도 다음 주기에 반드시 걸린다.
>
> **실행 중에 새 주문이 들어오면?** `ORDER_ID` 가 단조 증가하므로 새 행은 항상 커서 뒤쪽이고,
> 이번 실행에서 읽힌다. 설령 빠져도 `STATUS='N'` 이라 다음 주기가 처리한다 — 손실이 아니다.

**청크 상한(`max-chunks-per-run`, 기본 50)은 다른 목적이다.** 커서가 종료를 보장하므로
무한 루프 방지용이 아니라 **수행 시간의 상한**이다. 상한이 없으면 락 TTL 을 넘길 수 있고,
그때 배치가 겹쳐 돈다. 상한에 걸려 남은 일은 다음 주기가 이어받는다 —
배치에서는 "이번에 다 못 했다" 가 정상적인 결과다.

**청크마다 독립된 트랜잭션이다.** 3번째 청크가 실패해도 1·2번의 100건은 이미 확정되어
`STATUS='Y'` 다. 그 상태에서 `FAIL / processedCount=0` 으로 보고하면 **거짓**이다.
그래서 실패해도 그때까지의 건수를 보존해 `PARTIAL` + 에러 코드로 보고한다 —
D-14 가 세운 경계("예외 = 아무 데도 남지 않았다 / 반환 = 어딘가엔 남았다")를 청크 단위로 확장한 것이다.

### 4.7 배치 운영 요건

| 항목 | 규격 |
|---|---|
| 중복 실행 방지 | Redis 분산 락 `SET key token NX PX <ttl>`. 반납은 **Lua 로 토큰 비교 후 삭제** |
| 락 키 | `eai:lock:if-shp-001` (인터페이스마다 별개) |
| 락 TTL | **4분** (주기 5분보다 짧게 — 근거는 아래) |
| 멱등성 | **조회 조건 `STATUS='N'` + 단일 트랜잭션.** PK 위반 스킵 정책 철회 (D-22) |
| 부분 실패 | 실패 건은 `STATUS='N'` 유지 → 다음 주기 자연 재처리. 나머지는 진행 |
| 청크 | `FETCH FIRST 100 ROWS ONLY` + 커서 반복 (4.6) |
| 스케줄러 | `@Scheduled(fixedDelay)`. `fixedRate` 는 지연 시 실행이 밀려 쌓인다 |
| 스케줄러 스레드 | 풀 크기 **1**, 이름 `eai-batch-` |
| 자동 실행 스위치 | `inspien.batch.shipment.enabled`. **끄더라도 수동 트리거는 동작한다** |

**락 반납이 이 설계의 요점이다.** TTL 이 있으므로 수행이 TTL 을 넘기면 소유권이 조용히 사라진다.
그 뒤에 다른 실행이 락을 새로 잡았는데 우리가 `DEL` 을 부르면
**남의 락을 풀어 주고 세 번째 실행을 들여보낸다.**

```
A: 락 획득 (토큰 a, TTL 4분)
A: 수행이 5분 걸림 → 4분에 락 만료
B: 락 획득 (토큰 b)          ← 정상. TTL 의 존재 이유다
A: 수행 종료 → DEL           ← 여기서 b 를 지운다. B 는 자기가 락을 쥐고 있다고 믿는 중
C: 락 획득 → B 와 겹쳐 돈다
```

그래서 `GET` 으로 토큰을 비교한 뒤 지우며, 비교와 삭제도 원자적이어야 하므로 **Lua 스크립트**로
서버에서 실행한다. 토큰이 이미 남의 것이면 삭제하지 않고 **ERROR 로 기록한다** —
그 로그가 "수행이 TTL 을 넘었다 = 겹쳐 돌았을 수 있다" 는 유일한 단서다.

**TTL 을 주기보다 짧게 둔 이유.** 길게 두면 프로세스가 비정상 종료해 락을 반납하지 못했을 때
남은 TTL 동안 배치가 한 주기 이상 통째로 멈춘다. 짧게 두면 손실은 최대 한 주기로 제한되고,
수행이 TTL 을 넘긴 경우는 위의 토큰 불일치로 검출된다. 기동 시 `lockTtl < fixedDelay` 를 검증한다.

**Redis 가 죽으면 락 없이 진행하지 않는다.** 가용성을 위해 안전장치를 끄는 선택은 하지 않는다 —
되돌릴 수 없는 환경에서 중복 전송은 "잠시 멈춤" 보다 훨씬 나쁜 결과다.
`EAI-4006 BATCH_LOCK_STORE_ERROR` 로 실패시키고 회복은 다음 주기에 맡긴다.
**`EAI-4001`(락이 잡혀 있다)과 반드시 구분한다** — 전자는 인프라 장애, 후자는 정상 동작이며
조치가 정반대다. 한 코드로 묶으면 Redis 가 죽은 상태를 "정상적으로 겹침 방지 중" 으로 읽게 된다.

**스레드 풀 1과 분산 락은 대체 관계가 아니다.** `fixedDelay` + 단일 스레드면 인스턴스 안에서는
겹칠 수 없다. 락이 필요한 경우는 ① 인스턴스가 둘 이상일 때 ② **수동 트리거가 자동 주기와 겹칠 때**다
(수동 호출은 웹 요청 스레드에서 돌아 스케줄러 스레드와 무관하다 — 시연 자리에서 실제로 일어난다).
앞의 것은 **대기 없는 직렬화**이고 뒤의 것은 **겹침 검출**이다.

### 4.8 응답 포맷 / 엔드포인트

**수동 트리거**

```
POST /api/v1/shipments/batch
(본문 없음)
```

본문을 받지 않는 것은 의도다. `APPLICANT_KEY` 나 청크 크기를 파라미터로 받으면
**호출자가 다른 지원자의 주문을 조회하도록 만들 수 있는 문**이 열린다.
배치의 조회 기준은 **인터페이스의 정의**이지 요청의 내용이 아니다.

응답 형식은 3.10 과 동일하며 `ifId` 는 `IF-SHP-001`, `skipDetail` 의 사유는
`MISSING_ORDER_KEY` / `MISSING_SHIPPING_ADDRESS` 다.

| 결과 | 상태 | 언제 |
|---|---|---|
| `SUCCESS` | 200 | 전건 전송 완료 (0건 포함 — 할 일이 없었다) |
| `PARTIAL` | 200 | 스킵이 있거나, 청크 도중 실패해 일부만 확정됨 |
| `FAIL` + `EAI-4001` | **409** | 이전 주기가 아직 수행 중 — **정상 동작** |
| `FAIL` + `EAI-4006` | 503 | 락 저장소(Redis) 접근 실패 |
| `FAIL` + `EAI-2xxx` | 502 / 503 | 대상 DB 실패 |

> **락 미획득을 `SUCCESS / 0건` 으로 보고하지 않는 이유.** 겹침 방지는 정상 동작이지만
> **처리하지 못한 일이 남아 있다**는 사실은 감추지 않는다. 성공으로 보고하면 이력만 보고는
> "할 일이 없었다" 와 "이전 주기가 아직 돌고 있다" 를 구분할 수 없고, 후자가 계속되면
> 배치는 사실상 멈춘 상태다. 다만 HTTP 는 500 이 아니라 **409** 다 — 서버 결함이 아니라 상태 충돌이며,
> 호출자가 할 일은 "잠시 뒤 다시" 이지 "담당자에게 연락" 이 아니다.

## 5. 공통 — 운영 관점 (과제 3.3)

### 5.1 인터페이스 실행 로그

애플리케이션 로그와 **분리**하여 별도 파일로 출력한다 (요구사항: local 파일 저장).
출력 경로: `logs/interface/interface-yyyyMMdd.log`

| 항목 | 설명 |
|---|---|
| `TX_ID` | UUID. **실행 1건당 1개.** MDC 로 전 구간 전파 |
| `IF_ID` | `IF-ORD-001` / `IF-SHP-001` |
| `STEP` | `SENDER` / `VALIDATOR` / `MAPPER` / `RECEIVER_JDBC` / `RECEIVER_FTP` |
| `START` / `END` / `ELAPSED` | 시각 및 소요 ms |
| `RESULT` | `SUCCESS` / `PARTIAL` / `FAIL` / `ABORTED` |
| `COUNT` | 성공 / 스킵 / 실패 건수 분리 |
| `DETAIL` | 구간별 부가정보 (`PREPARE`/`COMMIT`, `CHUNK=n`, `TRIGGER=MANUAL` 등) |
| `ERROR` | 에러 코드 + 메시지 |

- 개인정보(`NAME`, `ADDRESS`)는 **애초에 실리지 않는다.** 건수·구간·결과·코드만 남기므로 스키마에 자리가 없다 — 마스킹으로 걸러내는 것보다 강한 통제다
- 구간이 결과 표시 없이 닫히면 `ABORTED` 로 남긴다. **조용히 사라지는 구간을 만들지 않는다**
- 사전 안내의 RTIMS(실시간 모니터링 솔루션) 사상을 축소 구현한 것

**구간은 프로토콜 단위로 나눈다 — 도메인 단위가 아니다.** `RECEIVER_JDBC` 이지
`RECEIVER_ORDER_TB` 가 아니다. 운영자가 알아야 하는 것은 "어느 종류의 상대 시스템에
연락할 것인가" 이고 그것은 테이블 이름이 아니라 프로토콜로 결정된다.
덕분에 **IF-SHP-001 을 추가하면서 구간이 하나도 늘지 않았다.**

**수신처마다 `PREPARE` 1줄 + `COMMIT` 1줄 (D-17).** 합치면 "업로드까지는 됐는데 확정에서
죽었다" 와 "업로드부터 실패했다" 를 구분할 수 없고, 전자는 수동 조치·후자는 재시도로
조치가 정반대다. 부수 효과로 이력 파일이 **보상 트랜잭션의 진행 순서를 그대로 보여주는 증거**가 된다.

**배치는 한 실행이 여러 청크를 돈다.** `txId` 는 실행당 1개이고 구간 줄은 청크마다 반복되며,
`DETAIL` 의 `CHUNK=n` 으로 구분한다. 청크마다 `txId` 를 새로 발급하지 않는 이유는
운영의 단위가 청크가 아니라 **"5분 주기가 한 번 돈 것"** 이기 때문이다.

### 5.2 예외 분류

| 분류 | 대상 | 처리 |
|---|---|---|
| `RetryableException` | FTP 커넥션 타임아웃, DB 일시 단절, Redis 단절 | 재시도 가능으로 분류 |
| `NonRetryableException` | 유효성 검증 실패, 매핑 오류, PK 위반, 확정 단계 실패 | 즉시 실패 처리 |

> 배치에서는 재시도 분류가 곧 "다음 주기" 를 뜻한다. 앱 안에서 즉시 재시도 루프를 돌리지 않는 이유는,
> 5분 뒤에 어차피 다시 오므로 **같은 일을 두 곳에서 하게** 되기 때문이다.

**에러 코드**

| 코드 | 의미 | 재시도 |
|---|---|---|
| `EAI-1001` | VALIDATION_ERROR | 불가 |
| `EAI-1002` | MAPPING_ERROR | 불가 |
| `EAI-1003` | SOURCE_PARSE_ERROR | 불가 |
| `EAI-1004` | SOURCE_ENCODING_ERROR | 불가 |
| `EAI-2001` | JDBC_CONN_ERROR | 가능 |
| `EAI-2002` | JDBC_EXEC_ERROR | 불가 |
| `EAI-3001` | FTP_CONN_ERROR | 가능 |
| `EAI-3002` | FTP_UPLOAD_ERROR (준비 단계 — DB 가 함께 롤백된다) | 가능 |
| `EAI-3004` | FTP_ENCODING_ERROR (파일명 또는 내용 인코딩 손상) | 불가 |
| `EAI-3005` | FTP_COMMIT_FAILED (**확정 단계** 업로드 실패 — 수동 조치) | 불가 |
| `EAI-4001` | BATCH_LOCK_ACQUIRE_FAILED (**이전 주기 수행 중 — 정상 동작**) | 불가 |
| `EAI-4002` | ID_ISSUE_FAILED (Redis 단절) | 가능 |
| `EAI-4003` | ID_SPACE_EXHAUSTED (26,000 소진) | 불가 |

| `EAI-4005` | FLOW_ERROR (파이프라인 실행 오류 — 구간에 귀속되지 않는 예외) | 불가 |
| `EAI-4006` | BATCH_LOCK_STORE_ERROR (**락을 확인할 수 없다** — 인프라 장애) | 가능 |

> `EAI-3003 FTP_COMPENSATION_FAILED` 는 **제거됨** (D-21 — 보상할 원격 상태가 없어졌다).
> 번호는 재사용하지 않는다. 과거 로그에 남아 있을 수 있고, 같은 번호가 다른 의미를 갖는 것이
> 코드 체계에서 가장 나쁜 일이다.

**대역 구분의 목적은 "전화를 누구에게 걸지" 다.**

```
1xxx  메시지 자체의 문제   (송신 시스템 / 데이터)
2xxx  JDBC 구간
3xxx  FTP 구간
4xxx  공통 운영 (배치 제어 · 채번 · 전달 조율 · 파이프라인)
```

**타임아웃 (명시 설정 — 기본값 무한 대기가 실제 장애의 주범)**

| 대상 | 항목 | 값 |
|---|---|---|
| Oracle | `oracle.net.CONNECT_TIMEOUT` | 10s |
| Oracle | `oracle.jdbc.ReadTimeout` | 20s |
| Oracle | `Statement.setQueryTimeout` | 20s |
| Oracle | Hikari `connectionTimeout` (풀 대기) | 15s — 드라이버 connect 보다 길게 |
| FTP | connectTimeout / dataTimeout | 10s / 15s |
| Redis | connect-timeout / timeout | 2s / 2s — 채번이 실시간 응답 경로 위에 있다 |

## 6. 설계 결정 기록

| ID | 쟁점 | 채택 | 근거 |
|---|---|---|---|
| D-01 | HEADER.STATUS 처리 | trim 후 `N` 로 정규화 | 배치 조회 조건이 `STATUS='N'`. 샘플은 15건 모두 `N` 이라 실질 영향 없음 |
| D-02 | 고아 ITEM / 빈 HEADER | **건 단위 스킵 + PARTIAL** | 샘플에 11건이 의도적으로 심어져 있음. 전체 거부 시 63건도 적재 불가 |
| D-03 | 채번 부여 단위·진행 방식 | **행 단위 + 순차 증가** | 행 단위는 PK `(ORDER_ID, APPLICANT_KEY)` 제약상 유일한 선택지. 순차는 재현성·추적성 우위 |
| D-04 | 두 테이블 트랜잭션 | **단일 트랜잭션** | B3 — 동일 인스턴스·동일 계정 확인됨. 기동할 때마다 재확인 |
| D-05 | 배치 동시성 | **분산 락만** | 단일 인스턴스 실행. `SELECT FOR UPDATE` 는 과잉 |
| D-06 | 시연 조회 기준 | `CREATE_TIME` 활용 | DEFAULT `SYSDATE`, DB 시간대 `Asia/Seoul` → 로컬 날짜와 일치 |
| D-07 | 영수증 파일 내용 인코딩 | **EUC-KR**, 설정 외부화 | 원본 XML 인코딩 계승 |
| D-08 | 로컬 Docker DB | 미사용 | 대상이 Oracle 19c 로 확정. MySQL 컨테이너는 충실한 테스트 대역이 아님 |
| D-09 | 채번 저장소·폴백 | **Redis `INCRBY` + DB `MAX` 시딩.** DB 시퀀스 테이블 철회 | 시퀀스 테이블은 대상 스키마 변경. 대체 채번기 자동 전환은 두 채번기가 동시에 살아 있는 순간 중복을 만든다 |
| D-10 | 공간 소진 시 | `EAI-4003` 실패, 리셋은 앱 밖 도구 | 카운터를 되돌리는 경로가 앱 안에 있으면 설정 실수로 운영에서 실행된다 |
| D-11 | JDBC 트랜잭션 경계 관리 | **커넥션을 객체가 직접 보유** (`PendingCommitDelivery`) | `@Transactional`·`TransactionTemplate` 은 경계가 **한 메서드 안에 닫힌다**는 전제인데, 우리 경계는 `prepare()`→`commit()` 이고 그 사이에 FTP 가 낀다. `PlatformTransactionManager` 직접 사용은 트랜잭션을 **ThreadLocal 에 묶어** 제약을 타입에 드러내지 않는다. **대가**: FTP 업로드 시간만큼 DB 커넥션 점유 → 풀 5, FTP 타임아웃 명시로 방어 |
| D-12 | 접속정보 주입 경로 | `spring.datasource.*` 미사용, `DataSourceAutoConfiguration` **배제** | 자동 설정은 크리덴셜을 설정 파일로 **한 번 더 복사**하게 만들고, 그 복사본이 커밋 사고의 경로다. 또 제어 평면이 "URL 이 없다" 며 죽는다 |
| D-13 | 채번 시딩 실행 시점 | `@Bean(initMethod)` — 컨텍스트 갱신 중 | `ApplicationRunner` 는 **웹 서버가 요청을 받기 시작한 뒤** 에 돈다. 실패 시 **기동 중단** — 복원 없이 뜨면 첫 요청부터 PK 위반 |
| D-14 | 전달 조율 결과 표현 | 반환을 `int` → **`DeliveryOutcome`** | 3.9 표 4번 행은 **예외로 표현하면 안 되는 상태**다. DB 에 63행이 유효한데 `FAIL` 로 응답하면 호출자가 재요청하고, 그 재요청이 곧 중복 적재다. **예외 = "아무 데도 남지 않았다" / 반환 = "어딘가엔 남았다"** |
| D-15 | 보상 성공 여부 집계 | `compensate()` 를 반환값 없이 유지 | 보상 실패는 각 `Delivery` 가 직접 기록한다. 보상은 **이미 다른 실패를 처리하는 중**에 불리므로, 그 결과로 다시 분기하는 코드는 실패 경로를 한 겹 더 복잡하게 만든다 |
| D-16 | `txId` 발급 주체 | **`IntegrationFlow` 가 발급**, Sender 는 받아서 쓴다 | Sender 가 만들면 파싱 실패 시 **추적 ID 자체가 없어** 이력도 응답도 남길 수 없다. `txId` 는 메시지의 속성이 아니라 **실행 단위의 식별자**다 |
| D-17 | 수신처 구간 로그 단위 | 수신처마다 **`PREPARE` + `COMMIT`** 2줄 | 합치면 수동 조치와 재시도를 구분할 수 없다. 이력이 보상 트랜잭션 순서의 증거가 된다 |
| D-18 | 응답의 `txId` 전달 경로 | **`ProcessResult` 가 직접 보유** | 그 값은 실행 중에만 MDC 에 있고 `complete()` 에서 해제된다. 이 값은 결과의 부가 정보가 아니라 **신원**이다 |
| D-19 | HTTP 상태 코드 매핑 | `PARTIAL` 은 **200**, `FAIL` 은 대역별 4xx/5xx, `EAI-4001` 은 **409** | 상태 코드의 실질적 역할은 **호출자의 다음 행동을 정하는 것**이다. 수동 조치가 필요한 `PARTIAL` 에 5xx 를 주면 **재시도 로직이 곧 중복 적재**가 된다. `default` 없는 exhaustive switch |
| D-20 | 컨트롤러 빈 등록 방식 | 컨트롤러만 **컴포넌트 스캔** 허용 | `@RestController` 는 `@Component` 계열이라 스캔과 `@Bean` 등록이 겹치면 **같은 핸들러가 두 번 등록**되어 기동이 실패한다. 단 flow config 와 **동일한 `@ConditionalOnProperty`** 를 건다 |
| D-21 | FTP 보상 트랜잭션 구조 | **업로드를 준비 → 확정 단계로 이동.** `.tmp` + rename 철회, `EAI-3003` 제거 | **실측이 전제를 깨뜨렸다.** 서버가 rename 을 거부하고(`451`) Oracle 은 `DELETE` 가 없다(`ORA-01031`). 두 시스템 모두 append-only 이므로 `.tmp` 방식은 **매 실행 반드시 실패**하고 보상 경로도 실행 불가다. **보상 트랜잭션 설계의 첫 질문은 "보상이 이 환경에서 가능한가" 이며**, 불가능하면 준비 단계의 부수효과를 없애야 한다. **결과적으로 실패 경로가 더 단순해졌다.** **대가**: 전송 중단 시 잘린 파일이 회수 불가로 남는다 → 크기까지 검증해 검출 |
| **D-22** | **배치 멱등성의 근거** | **`STATUS='N'` 조회 조건 + 단일 트랜잭션.** 초판의 "PK 위반은 이미 처리된 건으로 간주해 스킵" **철회** | 초판 정책은 **우리 구조에서 성립하지 않는다.** `SHIPMENT_ID` 를 우리가 채번하므로 같은 주문을 두 번 처리해도 **PK 는 다르다** — PK 위반으로 걸러질 일이 애초에 없다. 반대로 PK 위반이 실제로 났다면 그것은 "이미 처리됨" 이 아니라 **채번 카운터가 적재 이력보다 뒤에 있다**는 뜻이며(Redis 초기화 후 시딩 실패 등), 스킵하면 그 손상을 조용히 덮고 다음 주기에 또 만난다. 그래서 **실패시킨다**. 실제 멱등성은 다른 곳에서 온다 — 커밋 성공 시 `'Y'` 라 다시 읽히지 않고, 커밋 실패 시 배송 지시도 만들어지지 않는다. **중간 상태가 없다** |
| **D-23** | **배치의 이상 데이터 처리** | **치명적 위반을 두지 않는다 — 전부 건 단위 스킵** | IF-ORD-001 은 호출자가 기다리므로 전체 거부가 성립하지만, 배치에는 **고쳐 줄 호출자가 없다.** 전체 거부는 다음 주기도, 그다음 주기도 같은 판단을 반복하게 만들어 **잘못된 1건이 정상 99건을 영구히 막는다.** D-02(부분 처리)를 배치의 성격에 맞게 옮긴 것이다. **대가**: 스킵된 행이 `'N'` 으로 남아 매 주기 다시 읽히고 같은 경고가 반복된다. `STATUS='E'` 로 밀어내면 멈추지만 그것은 **대상 시스템의 어휘를 우리가 늘리는 일**이라 "기존 스키마 불변" 과 충돌한다. 반복을 감수하고 기록하기로 했다 (4.5) |
| **D-24** | **후행 상태 갱신의 로그 구간** | `Step.STATUS_UPDATE` **제거.** `RECEIVER_JDBC` 한 구간으로 기록 | 갱신은 INSERT 와 **동일 트랜잭션**이므로 "적재는 됐는데 갱신은 안 됐다" 는 상태가 **구조적으로 존재할 수 없다.** 그런데도 구간을 나누면 로그가 **존재하지 않는 상태를 표현 가능한 것처럼** 보이게 만들고, 운영자는 "RECEIVER_JDBC 는 SUCCESS 인데 STATUS_UPDATE 줄이 없는" 경우를 찾아다니게 된다. 건수도 잃지 않는다 — 두 문장이 같은 레코드 리스트를 소비하므로 적재 건수와 갱신 건수는 **항상 같고**, `COUNT` 열에 이미 있다 |
| **D-25** | **`SkipReason` 이 엔진에 도메인 어휘를 갖는 문제** | **열거형 유지.** 문자열 코드 + 인터페이스별 열거형으로의 분리는 하지 않음 | 알고 있는 한계다 — `ORPHAN_ITEM` 은 주문의 사정이고 `MISSING_SHIPPING_ADDRESS` 는 배송의 사정이니, 인터페이스가 늘 때마다 엔진이 커진다. 원칙대로라면 `Step` 을 프로토콜 단위로 유지한 것처럼 내려야 한다. 그럼에도 유지하는 이유는 **이 이름들이 사실상 외부 계약**이기 때문이다 — `skipDetail` 을 거쳐 응답 JSON 과 이력 파일에 그대로 나간다. 열거형이면 상수를 바꿀 때 컴파일이 깨지지만, 문자열로 열면 오타 하나가 **조용히 새 사유 분류를 만들어** 집계를 둘로 쪼갠다. 그 보호를 잃는 대가가 지금 규모에서 더 크다 |
| **D-26** | **배치 청크 반복 방식** | **keyset 페이징 (`ORDER_ID > :cursor`).** "0건까지 반복" 과 `OFFSET` 모두 미채택 | 스킵된 행은 `'N'` 으로 남아 **같은 조건으로 다시 조회된다.** 그래서 "0건까지" 는 무한 루프이자 집계 부풀림이고(스킵 11건이 40건으로 나간다), `OFFSET` 은 처리된 행이 결과 집합에서 빠지므로 **아직 처리하지 않은 행을 건너뛴다.** 커서는 `[A-Z][0-9]{3}` 고정 제로패딩 덕에 성립한다(사전식 정렬 = 채번 순서). **커서는 영속화하지 않는다** — 저장하면 커서보다 작은 미처리 행이 영구 유실되고, 실행마다 처음부터 읽으면 어떤 이유로 빠진 행도 다음 주기에 걸린다. 청크 상한은 무한 루프 방지가 아니라 **락 TTL 안에 수행 시간을 묶기 위한** 별개 장치다 |

## 7. 시연 절차 (면접 대비)

### 7.1 사전 준비

```powershell
# 콘솔 한글 출력
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8

docker compose up -d              # Redis
.\gradlew.bat bootstrapRun        # BOOT-000: 저장된 응답으로 접속정보 복원
.\gradlew.bat probeRun            # BOOT-001: 연계 대상 접속 확인
```

> ⚠️ **대상 환경은 append-only 이고 지원자 전원이 공유한다.** 재실행할 때마다 ORDER_TB 에
> 행이 누적되고 되돌릴 수 없다. 시연 직전에 한 번만 깨끗하게 실행할 것.

### 7.2 IF-ORD-001 — 실시간 주문 연계

```powershell
.\gradlew.bat bootRun

# 별 창에서
curl.exe -X POST http://localhost:8080/api/v1/orders `
  -H "Content-Type: application/octet-stream" `
  --data-binary "@secrets/sample-data.euckr.xml"
```

> `-H "Content-Type: application/octet-stream"` 를 **반드시** 붙인다. 생략하면 curl 이
> 폼 인코딩해 본문이 부풀고 파서가 0건을 반환한다.

기대 응답: `result=PARTIAL`, `processedCount=63`, `skippedCount=11`
(`ORPHAN_ITEM=7`, `HEADER_WITHOUT_ITEM=4`)

**DB 확인**

```sql
SELECT * FROM ORDER_TB
 WHERE APPLICANT_KEY = '<내 키>'
   AND TRUNC(CREATE_TIME) = TRUNC(SYSDATE)
 ORDER BY ORDER_ID;
```

**FTP 확인** — 서버가 `RETR` 을 거부하므로(B10) **파일을 받아 열어보는 시연은 불가능하다.**
과제 5.1 의 "업로드 결과 파일 확인" 은 아래 세 가지로 충족한다.

| 보일 것 | 무엇을 증명하는가 |
|---|---|
| `/Recruit/2026` 리스팅에 `INSPIEN_{한글이름}_*.txt` 가 **깨지지 않고** 보임 | 제어 채널 UTF-8 설정이 실제로 들었다 (3.7) |
| 같은 디렉터리의 다른 파일들은 `INSPIEN_???_...` | **기본값을 그대로 둔 클라이언트는 조용히 깨진다** — 대조가 근거가 된다 |
| 파일 크기가 0 이 아니고 행 수에 비례 | 전송이 중단되지 않았다 (업로드 검증이 보는 것과 같은 값) |

파일 **내용**은 DB 조회로 대신한다. 영수증 한 줄은 `ORDER_TB` 행에서 `STATUS` 를 뺀 뒤
순서를 바꾼 것이므로, 아래 쿼리가 **실제 전송된 내용과 같은 문자열**을 돌려준다.

```sql
SELECT ORDER_ID || '^' || USER_ID  || '^' || ITEM_ID   || '^' || APPLICANT_KEY
    || '^' || NAME     || '^' || ADDRESS  || '^' || ITEM_NAME || '^' || PRICE AS LINE
  FROM ORDER_TB
 WHERE APPLICANT_KEY = '<내 키>'
   AND TRUNC(CREATE_TIME) = TRUNC(SYSDATE)
 ORDER BY ORDER_ID;
```

> 리스팅 화면은 **미리 캡처해 둔다.** 한글이 살아있는 파일과 `?` 로 깨진 파일이 한 화면에
> 나란히 보이는 장면이, "인코딩을 왜 신경썼는가" 에 대한 가장 짧은 대답이다.

### 7.3 IF-SHP-001 — 운송사 전송 배치

두 가지 중 하나로 보인다.

```powershell
# (a) 수동 트리거 — 기다릴 필요 없다. 실행 이력에 TRIGGER=MANUAL 로 남는다
curl.exe -X POST http://localhost:8080/api/v1/shipments/batch

# (b) 5분 주기 대기 — 자동 실행을 보이려면 이쪽. 이력에 TRIGGER=SCHEDULED 로 남는다
Get-Content -Wait -Tail 20 logs\interface\interface-$(Get-Date -Format yyyyMMdd).log -Encoding UTF8
```

> 주기를 줄여 보여 주려면 `inspien.batch.shipment.fixed-delay: PT30S` (ISO-8601 표기 필수).
> **이때 `lock-ttl` 도 함께 줄여야 한다** (`PT20S` 등). 기동 시 `lockTtl < fixedDelay` 를 검증하므로
> 주기만 줄이면 바인딩 단계에서 **기동이 실패한다** (4.7 · 8.2 실측).
> 반대로 상태를 고정해야 하면 `inspien.batch.shipment.enabled: false` — **자동만 꺼지고
> 수동 트리거는 그대로 동작한다.**

기대 응답: `result=SUCCESS`, `processedCount=` 직전에 적재한 미전송(`STATUS='N'`) 행 수

**확인**

```sql
-- 배송 적재
SELECT * FROM SHIPMENT_TB
 WHERE APPLICANT_KEY = '<내 키>'
   AND TRUNC(CREATE_DATE) = TRUNC(SYSDATE)
 ORDER BY SHIPMENT_ID;

-- 상태 갱신 (미전송이 0건이어야 한다)
SELECT STATUS, COUNT(*) FROM ORDER_TB
 WHERE APPLICANT_KEY = '<내 키>'
 GROUP BY STATUS;
```

**멱등성 시연** — 수동 트리거를 한 번 더 누른다. `processedCount=0`, `result=SUCCESS` 가 나온다.
`STATUS='Y'` 로 닫혀 조회 대상에서 빠졌기 때문이며, 이것이 D-22 가 말하는 멱등성의 근거다.

**겹침 방지 시연 (1.2 정정)** — **두 창에서 동시에 누르는 방식은 쓰지 않는다.** 수행이 수십 ms 로
끝나 경합이 재현되지 않고, 만에 하나 락이 듣지 않으면 같은 주문이 두 벌 적재되어 **되돌릴 수 없다**(B10).
대신 락을 직접 걸어 두고 트리거한다 — 결정적이고, 행이 하나도 생기지 않는다.

```powershell
docker exec inspien-redis redis-cli SET eai:lock:if-shp-001 demo PX 30000
curl.exe -i -X POST http://localhost:8080/api/v1/shipments/batch   # 30초 안에
docker exec inspien-redis redis-cli DEL eai:lock:if-shp-001
```

`409` + `EAI-4001` 이 돌아오고, 실행 이력에는 `START` 와 `END` **두 줄만** 남는다.
락을 잡지 못해 파이프라인에 진입조차 하지 않았다는 사실이 구간 줄의 부재로 드러난다.

### 7.4 운영 관점 제시

```powershell
Get-Content logs\interface\interface-$(Get-Date -Format yyyyMMdd).log -Encoding UTF8
```

> **`-Encoding UTF8` 을 빠뜨리지 않는다.** PowerShell 5.1 은 BOM 없는 UTF-8 파일을 시스템
> 코드페이지(한글 Windows = MS949)로 읽는다. `type` 이나 옵션 없는 `Get-Content` 는
> **멀쩡한 이력의 한글을 깨뜨려 보여 준다.** 파일은 정상인데 화면만 깨지는 것이라,
> 시연 중에 나오면 정상 동작하는 시스템을 두고 인코딩을 해명하게 된다.
> `[Console]::OutputEncoding` 은 출력 인코딩이라 이 문제를 막지 못한다 (8.2 실측).

한 실행의 이력이 `START → SENDER → VALIDATOR → MAPPER → RECEIVER_JDBC(PREPARE) →
RECEIVER_FTP(PREPARE) → RECEIVER_JDBC(COMMIT) → RECEIVER_FTP(COMMIT) → END` 로 남는다.
**이 순서 자체가 보상 트랜잭션 설계의 증거**이므로 발표 자료에 그대로 쓴다.

## 8. 검증 이력

설계가 의도대로 동작했는지를 **실물 대상으로** 확인한 기록이다.
"돌려 봤다" 가 아니라 **"무엇을 관측해 무엇을 단언할 수 있게 됐는가"** 를 남긴다.

### 8.1 IF-ORD-001 (2026-07-30)

| 항목 | 결과 |
|---|---|
| 응답 | `PARTIAL` / `processedCount=63` / `skippedCount=11` (`ORPHAN_ITEM=7`, `HEADER_WITHOUT_ITEM=4`) |
| ORDER_TB | 63행 적재 |
| 영수증 FTP | 최종 파일명으로 전송, 파일명·내용 한글 정상 |

샘플에 의도적으로 심어둔 11건이 응답의 `skipDetail` 로 그대로 드러났다 — D-02 가 말하는
"버린 건수를 반드시 드러낸다" 가 산출물로 확인된 지점이다.

### 8.2 IF-SHP-001 (2026-07-31)

**전제 상태** — `ORDER_TB` 에 `STATUS='N'` 126행(IF-ORD-001 2회 실행분), `SHIPMENT_TB` 0행.
126 > 청크 상한 100 이므로 **청크 반복 경로가 이번 실행에 포함됐다** — 63건이었다면 1청크로 끝나
가장 위험한 코드 경로를 못 보고 지나갔을 것이다.

| 확인 항목 | 결과 | 관측 근거 |
|---|---|---|
| 채번 시딩 (D-09 · D-13) | 통과 | 기동 로그 `MAX(ORDER_ID)=A125` — 적재 126행과 일치. 다음 발급은 `A126` |
| 대상 동일성 (D-04) | 통과 | 기동마다 재확인 로그 출력 — 전제가 깨지면 기동이 멈춘다 |
| 락 충돌 (D-19) | 통과 | `409` + `EAI-4001`. 이력은 `START`·`END` **2줄만** — 파이프라인 미진입 |
| 전건 처리 | 통과 | `SUCCESS` / `processedCount=126` / `skippedCount=0` / 238ms |
| 청크 반복 (D-26) | 통과 | `CHUNK=1`(100건, `CURSOR=-`) → `CHUNK=2`(26건, `CURSOR=A099`). **3청크를 만들지 않음** |
| 트랜잭션 경계 | 통과 | 청크마다 `RECEIVER_JDBC` `PREPARE`/`COMMIT` 각 1줄 |
| 상태 갱신 (4.4 · D-24) | 통과 | `STATUS` 집계 `Y=126`, `N` 0건. `STATUS_UPDATE` 구간 없이 건수 보존 |
| 인코딩 | 통과 | `SHIPMENT_TB` 배송지 한글 정상 (`서울특별시 강남구`) |
| 멱등성 (D-22) | 통과 | 재실행 `processedCount=0` / `SUCCESS`. `SENDER` 0건 뒤 즉시 `END` — **빈 트랜잭션을 열지 않는다** |
| 커서 비영속화 (D-26) | 통과 | 재실행의 `SENDER` 가 `CURSOR=-` 로 시작 — 저장했다면 `A125` 가 찍혔을 것 |
| 설정 검증 (4.7) | 통과 | `fixed-delay=PT30S` + `lock-ttl=PT4M` → **바인딩 단계에서 기동 실패**. 커넥션 풀도 만들기 전 |
| 스케줄러 | 통과 | `TRIGGER=SCHEDULED`. 앞 실행의 `END` 로부터 30.0초 뒤 `START` — `fixedDelay` 의미론 그대로 |

**부수 발견.** `Get-Content` 는 `-Encoding UTF8` 없이는 이력 파일의 한글을 깨뜨려 보여 준다.
파일 손상이 아니라 읽기 인코딩 문제다 (7.4 반영).

**실물로 검증하지 않은 것.** 청크 도중 실패 시의 `PARTIAL` 보고(4.6)와 락 TTL 초과 시의
토큰 불일치 검출(4.7)은 단위 테스트로만 덮어 둔다. 실패를 일으키려면 **되돌릴 수 없는
행을 공유 환경에 남기게 되기 때문**이다 (B10). 검증하지 않은 것을 검증한 것처럼 적지 않는다.

### 8.3 면접 당일 실행 순서

위 검증으로 기존 126행은 전부 `STATUS='Y'` 가 됐다. 따라서 **당일에는 주문을 새로 보내야**
배치가 처리할 대상이 생긴다. 채번은 `A126` 부터 이어지므로 기존 행과 충돌하지 않는다.

> ⚠️ **기존 행의 `STATUS` 를 `'N'` 으로 되돌리지 않는다.** 그 행들은 이미 `SHIPMENT_TB` 에
> 대응 행을 가지고 있으므로, 되돌리면 다음 배치가 **같은 주문에 배송 지시를 한 벌 더 만든다.**
> 지울 수도 없다(B10). 시연을 위해 상태를 손보는 것은 D-22 가 구조적으로 막아 둔 사고를
> **손으로 만들어 넣는 일**이다. 새로 쓰는 편이 더 쉬워 그럴 이유도 없다.

| 순서 | 할 일 | 보여 줄 것 |
|---|---|---|
| 사전 (발표 전) | 콘솔 인코딩 → `docker compose up -d` → `bootstrapRun` → `probeRun` → 빌드 1회 | — |
| 1 | `.\gradlew.bat bootRun` | 채번 시딩·D-04 재확인 로그 |
| 2 | IF-ORD-001 주문 전송 (7.2) | `PARTIAL` 63/11 — 버린 건수를 드러낸다 |
| 3 | ORDER_TB 조회 (참여자명·당일) + FTP 영수증 다운로드 | 과제 5.1 시연 요구사항 |
| 4 | IF-SHP-001 수동 트리거 (7.3) | `SUCCESS` — 청크·구간 이력 |
| 5 | SHIPMENT_TB 조회 + `STATUS` 집계 | 적재와 갱신이 같은 트랜잭션임 |
| 6 | 멱등성 1회 · 겹침 방지 1회 | `0건/SUCCESS`, `409/EAI-4001` |
| 7 | 이력 파일 통독 (7.4) | 구간 순서 = 보상 트랜잭션의 증거 |

자동 실행을 보일 필요가 있으면 4번 전에 주기를 줄여 띄운다 — `fixed-delay` 와 `lock-ttl` 을
**함께** 줄여야 하며(7.3), 이때 4번 수동 트리거는 생략한다.
