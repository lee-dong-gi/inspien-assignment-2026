## 1. 왜 EAI 인가 — 쉬운 말 버전

주문이 들어오면 그 정보가 여러 곳으로 가야 한다. 주문 DB, 영수증 파일, 운송사.

가장 쉬운 방법은 쇼핑몰이 직접 다 하는 것이다. 그러면 **쇼핑몰이 FTP 주소도 알아야 하고,
DB 접속정보도 알아야 하고, 운송사 파일 포맷도 알아야 한다.** 수신처가 하나 늘 때마다
쇼핑몰 코드를 고쳐야 하고, 시스템이 5개면 연결선이 20개가 된다.

그래서 가운데에 하나를 둔다. 쇼핑몰은 **그 하나에게만** 보내고 나머지는 가운데가 알아서 한다.

**사전 안내의 "ERP 는 통합, EAI 는 연결"** 이 이 이야기다.
통합은 시스템을 하나로 합치는 것이고, 연결은 기존 시스템을 그대로 둔 채 사이를 잇는 것이다.

여기서 원칙 하나가 나온다 — **우리는 데이터를 소유하지 않는다.**
주문 테이블도 운송 테이블도 우리 것이 아니고, 우리 편하자고 컬럼을 바꾸지 않는다.
**JPA 를 안 쓴 이유가 이것이다.** 엔티티를 만드는 순간 "우리가 주문을 가지고 있다" 는 신호가 된다.

## 2. 두 인터페이스의 관계 (핵심 4줄)

질문을 받으면 이 네 줄로 답한다.

1. **IF-ORD-001** — 손님이 주문한다 → 주문을 기록하고 영수증을 만든다
2. **IF-SHP-001** — 기록된 주문을 운송사에 넘긴다 (배송을 시켜야 하니까)
3. `STATUS` 컬럼이 둘을 잇는다. ORD 가 `'N'`(미전송)으로 기록하고, SHP 가 가져가 `'Y'` 로 바꾼다
4. Redis 락은 **IF-SHP-001 실행끼리** 겹치는 것을 막는다

### 자주 나올 오해 두 가지

| 오해 | 사실 |
|---|---|
| IF-SHP-001 은 누락 보정용 프로세스 | **아니다.** 별개의 업무 흐름이다. 주문받는 일과 택배 보내는 일은 다른 일이고, 하나는 즉시·하나는 모아서 처리하는 것이 자연스럽다. 과제도 "실시간과 배치를 구분해 구현하라" 를 명시했다 |
| Redis 락은 두 인터페이스가 겹치는 것을 막는다 | **아니다.** 배치 수행이 5분을 넘기면 다음 주기와 겹쳐 같은 주문이 두 번 나간다. 그리고 시연 자리에서 자동 주기 도중 수동 트리거를 누르면 역시 겹친다. 그것을 막는다 |

### "결합을 낮춘다" 의 실제 모습

두 인터페이스는 **서로를 직접 호출하지 않는다.** IF-ORD-001 은 IF-SHP-001 의 존재를 모르고
반대도 마찬가지다. 둘 사이의 유일한 접점은 **테이블의 상태값 하나**다.

그래서 **배치가 죽어 있어도 주문은 계속 받을 수 있고**, 나중에 배치를 켜면 밀린 것부터 처리한다.
사전 안내가 말하는 "시스템 간 결합을 낮춘다" 가 코드에서 이런 모습으로 나타난다.

## 3. Coordinator — 한 줄 정의

> **여러 곳에 보낼 때의 "순서와 실패 처리" 만 전담하는 칸.**

데이터가 뭔지도 모르고, 상대가 DB 인지 FTP 인지도 모른다.
"준비시키고, 다 되면 확정시키고, 아니면 되돌린다" 만 안다.

### 왜 만들었나 (이 순서로 설명하면 통한다)

과제가 준 구조는 세 칸이다 — `Sender → 변환 → Receiver`.
수신처가 하나면 충분한데, IF-ORD-001 은 **수신처가 둘**이다. 그러면 질문이 생긴다.

- 누가 먼저 가야 하나?
- DB 는 성공했는데 FTP 가 실패하면 **누가 DB 를 롤백시키나?**
- 둘 다 준비됐는지 **누가 판단하나?**

세 칸에는 이걸 맡을 자리가 없다. Receiver 는 자기 일만 알지 옆 Receiver 의 사정을 모르고,
Mapper 에 넣으면 변환 로직에 트랜잭션 제어가 섞인다.

### 계약 4개

```
1. 등록 순서대로 prepare()          → JDBC 먼저, FTP 나중
2. 하나라도 실패하면 역순으로 compensate()
3. 다 됐으면 등록 순서대로 commit()
4. 커밋 확정 후의 실패는 PARTIAL 로 보고 (예외를 던지지 않는다)
```

- **왜 JDBC 먼저인가** — 뒤집으면 이미 배포된 영수증을 회수해야 한다. 되돌릴 수 있는 쪽을 먼저 확정한다
- **왜 보상은 역순인가** — 나중에 만든 것부터 정리한다. 스택을 되감는 것과 같다
- **4번이 핵심** — 예외를 던지면 호출자는 "아무 일도 안 일어났다" 로 해석하고 재시도하는데,
  실제로는 63행이 들어가 있어 그 재시도가 곧 중복 적재다

> **예외 = 아무 데도 남지 않았다 / 반환값 = 어딘가엔 남았다**

**부수 효과** — Coordinator 가 수신처를 리스트로 받으므로, IF-SHP-001 은 **하나만 등록**하면
그대로 재사용된다. 같은 코드가 수신처 1개짜리 배치와 2개짜리 실시간을 모두 처리한다.

## 4. 보상 트랜잭션 — 설명 순서

### (1) 문제

> DB 는 롤백이 된다. **파일은 안 된다.**
> 그런데 과제는 "둘 다 처리됐을 때 결과를 반환하라" 고 요구한다.

DB 먼저 커밋하고 FTP 가 실패하면 63행을 되돌릴 수 없다.
FTP 먼저 올리고 DB 가 실패하면 영수증만 나가 있다.

### (2) 기본 아이디어 — 확정을 미룬다

```
prepare : DB 에 INSERT 만 하고 커밋은 안 한다   →   FTP 도 준비만 한다
          ↓ 둘 다 성공했나?
commit  : DB 커밋                              →   FTP 업로드
```

2PC 를 안 쓴 것이 아니라 **못 쓴다** — FTP 는 XA 리소스가 아니라 선택지가 아니었다.

### (3) 여기서 설계가 한 번 뒤집혔다 (발표의 절정)

처음엔 교과서대로 짰다. FTP 도 준비 단계에서 `.tmp` 로 올려두고, 확정 때 이름을 바꾸고,
실패하면 `.tmp` 를 지운다.

그런데 **서버가 이름 바꾸기를 거부했다**(`451`). 지우기도 거부했고(`550`),
오라클도 `DELETE` 권한이 없었다(`ORA-01031`).

즉 **보상 경로 자체가 실행 불가능한 코드**였다. 그래서 판단을 바꿨다.

> **되돌릴 수 없는 환경에서는 되돌리는 로직을 정교하게 짜는 게 아니라,
> 되돌릴 게 안 생기게 만들어야 한다.**

이제 FTP 준비 단계는 서버에 아무것도 쓰지 않는다. 확정 시점에 최종 이름으로 딱 한 번 올린다.
`.tmp` 개념 자체가 사라졌고 **실패 경로가 오히려 단순해졌다.**

### (4) 남는 구멍은 인정한다

DB 는 커밋됐는데 FTP 업로드가 실패하는 경우는 못 막는다.
이것을 `FAIL` 로 응답하지 않는 이유가 (2)-4번과 같다.

## 5. PARTIAL 은 두 종류다 ★ 면접 함정

*"PARTIAL 이면 뭘 해야 하죠?"* 에 **"재업로드요"** 라고만 답하면 절반만 맞은 것이 된다.

| 어떤 PARTIAL | 원인 | 사람이 할 일 | 구분법 |
|---|---|---|---|
| **스킵으로 인한 부분 처리** | 고아 ITEM 7건 등 이상 데이터 | **없음.** 우리 쪽 문제가 아니다 | 에러 코드 없음 |
| **커밋 확정 후 FTP 실패** | DB 는 들어갔는데 파일이 안 올라감 | **있음.** 파일 수동 업로드 | `EAI-3005` |

IF-ORD-001 실측의 `PARTIAL / 63 / 11` 은 **첫 번째**다. 파일은 정상 전송됐고,
11건은 원본 XML 에 애초에 짝이 없던 데이터라 **재처리할 대상 자체가 없다.**
조치 주체는 데이터를 보낸 쪽이지 우리가 아니다.

## 6. 영수증 실물 — 이 5줄이 설계를 압축한다

```
A000^USER01^ITEM01^LDK00021^김철수^서울특별시 강남구^맨투맨^29000
A001^USER01^ITEM02^LDK00021^김철수^서울특별시 강남구^후드티^35000
A002^USER02^ITEM03^LDK00021^이영희^서울특별시 서초구^라운드티^15000
A003^USER02^ITEM04^LDK00021^이영희^서울특별시 서초구^브이넥티^16000
A004^USER02^ITEM05^LDK00021^이영희^서울특별시 서초구^니트^42000
```

**슬라이드에 그대로 넣는다.** "1:N 을 평탄화했다" 를 말로 설명하는 것보다 이 화면이 빠르다.

| 관전 포인트 | 무엇이 보이는가 |
|---|---|
| `USER01` 이 2줄, `USER02` 가 3줄 | HEADER 1건 : ITEM N건 → **N행으로 평탄화**. 이름·주소가 반복되는 것이 증거 |
| `A000`~`A004` 가 줄마다 다름 | 채번이 **주문 라인 단위**다. 헤더 단위였다면 `USER01` 두 줄이 같은 번호 |
| `STATUS` 가 없음 | DB 9필드 / 파일 8필드. **필드 순서도 DB 와 다르다** (`ITEM_ID` 다음이 `APPLICANT_KEY`) |

> 이 쿼리로 언제든 재현할 수 있다 (정의서 7.2). FTP 는 `RETR` 이 막혀 있어 **파일을 받아
> 열어보는 시연은 불가능**하므로, 내용 확인은 이 방법이 유일하다.

## 7. 인코딩이 한 군데가 아니라 세 군데다

| 대상 | 인코딩 | 놓치면 |
|---|---|---|
| 받는 샘플 XML | EUC-KR | UTF-8 로 읽으면 한글이 깨진 채 DB·파일까지 전파 |
| 영수증 **내용** | EUC-KR | 원본 계승 |
| 영수증 **파일명** | **UTF-8** | 라이브러리 기본값 ISO-8859-1 이라 한글이 `?` 로 바뀌어 올라간다 |

파일명이 별개인 이유는 **FTP 가 명령 채널과 데이터 채널을 따로 쓰고, 파일명은 명령 채널로
나가기** 때문이다. 그리고 이 사고는 **예외가 나지 않는다.**

## 8. 반복해서 쓸 수 있는 문장들

> **에러를 내며 죽는 실패보다 조용히 틀리는 실패가 훨씬 위험하다.**
> (접속정보 평탄화 사고 · 파일명 `?` 치환 · 인코딩 불가 문자)

> **검증은 방어가 아니라 판단이다.**
> 일어날 수 없는 일을 검사하는 코드는 읽는 사람에게 "이 경우가 일어날 수 있다" 는
> 잘못된 정보를 준다. (길이 검증을 배치에서 뺀 근거 — 4.5)

> **같은 제약이 한쪽에서는 재설계를 강요하고 다른 쪽에서는 보장으로 쓰인다.**
> append-only 가 D-21 에서는 보상 트랜잭션을 뒤집게 만들었지만,
> 4.4 에서는 "읽은 행이 사라질 수 없으므로 PK UPDATE 는 반드시 1행" 의 근거가 된다.
> **"환경을 추측하지 않고 실측했다" 의 가장 좋은 예다.**

> **이해하지 못한 결정은 뒤집을 수 없다.**
> (AI 활용을 묻는 질문에 대한 답 — 설계 결정 26건 중 D-22 는 스스로 철회한 것이다)
